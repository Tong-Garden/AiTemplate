Create Company Flow
From the New Company form to the stored record
The form validates with Zod first, then the store calls the service, which validates again, maps to a DTO and posts it. The backend trims and checks every field before saving.
sequenceDiagram actor U as Administrator participant FE as Company Form participant ST as Company Store participant API as Backend API participant SV as Company Service U->>FE: Fill name address phone timezone FE->>FE: Zod validation FE->>ST: createCompany ST->>API: POST /v1/companies API->>SV: create SV->>SV: Trim and validate fields SV->>SV: Check name is unique SV-->>API: Company saved API-->>ST: 201 with company ST->>API: GET /v1/companies for current page ST-->>FE: Close dialog and show snackbar FE-->>U: New company in the list

States a company record moves through

Edit Company Flow
Inline editing in the grid with validation
Double clicking a row opens inline edit. Only the saved fields are sent. If the server rejects the change, the page is reloaded so the grid shows the real data.
graph TD A[Double click a row] --> B[Edit fields inline] B --> C[Click Update] C --> D{Grid rules pass?} D -->|No| B D -->|Yes| E[Zod validation in service] E --> F[PUT /v1/companies id] F --> G{Server accepts?} G -->|Yes| H[Store patches the row] H --> I[Show updated snackbar] G -->|No| J[Show error snackbar] J --> K[Reload current page]

Delete Company Flow
Removing one or more companies
Selected rows are deleted one by one. After each delete the store reloads the page, and steps back one page when the last row of a later page was removed.
graph TD A[Select row in grid] --> B[Click Delete] B --> C[DELETE /v1/companies id] C --> D{Found?} D -->|No| E[Show not found error] E --> F[Reload current page] D -->|Yes| G[Show deleted snackbar] G --> H{Last row on page above 1?} H -->|Yes| I[Load previous page] H -->|No| J[Reload same page]

DIAGRAM 6 OF 10
List With Pagination
How a page of companies reaches the screen
The backend slices the data and returns total counts in meta. The store keeps the full meta and the UI renders Previous, Next, page numbers, page size and the X of Y total text.
graph TD A[Request page and limit] --> B[Zod checks page 1 plus and limit 1 to 100] B --> C[GET /v1/companies] C --> D[Repository slices by offset and limit] D --> E[Response with data and meta] E --> F[Store saves companies and pagination] F --> G[Grid shows rows] F --> H[Pagination shows pages and total] H --> I{User changes page or size} I -->|Page| A I -->|Size| J[Reset to page 1] J --> A

Get Company By Id
Reading one company
The API exposes a single company by id and the store can load it as the selected company. An unknown id produces a not found error in the standard envelope.

Error Handling
How each failure reaches the user
Every backend error uses the envelope with type, title, status, detail and field. The API client turns it into structured errors, the store keeps error, errors and fieldErrors for five seconds, and the UI shows them.
graph TD A[Request fails] --> B{Which error?} B -->|422 validation| C[Field error under the input] B -->|409 duplicate name| D[Conflict snackbar] B -->|404 not found| E[Not found snackbar] B -->|500 unexpected| F[Generic server error snackbar] B -->|Zod in browser| C C --> G[Store clears errors after 5 seconds] D --> G E --> G F --> G

Data Flow Architecture
Layers from the screen to the repository and back
Frontend follows UI to store to service to mapper to repo. Backend follows router to service to repository to domain entity, with an envelope response going back.
graph TD A[Companies page and grid] --> B[Zustand company store] B --> C[Services with Zod] C --> D[Mappers] D --> E[Repo with axios] E --> F[FastAPI router with EnvelopeRoute] F --> G[Company service] G --> H[Repository interface] H --> I[In memory repository] I --> J[Company entity] J --> K[Mapper to response schema] K --> L[Envelope response] L --> E
